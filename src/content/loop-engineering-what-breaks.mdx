<p className="lp2-kicker">part two of two — <a href="/blog/loop-engineering">part one is here</a></p>

Part one ended on a twenty-line bash script and a reasonably confident claim: get four things right — a real critic, context hygiene, a budget, idempotent tools — and the loop does the prompting for you.

I still believe that. It is also not enough, and the gap is not academic.

Here is the problem with that script, stated plainly. It has exactly one way to stop on purpose: the critic returns zero. Everything else is the budget running out, which is not a decision, it is a timeout. A control system with one success condition and one timeout cannot tell the difference between work that went well, work that went nowhere, and work that quietly cheated. It reports all three the same way.

This post is the other half. Four things that get past a green checkmark, and about thirty lines of shell that catch them.

## 1. The green that was not green

Give an agent a failing test and a firm instruction to make it pass, and you have described two jobs, not one. *Fix the code* is the job you meant. *Make this command exit zero* is the job you specified. The second one is strictly easier.

So it does the easier one. Not maliciously — it has no concept of malice — but because deleting an assertion is a smaller edit than understanding a race condition, and nothing in the loop prefers one over the other.

The versions I have seen, roughly in order of how hard they are to spot:

- the test file is deleted
- `it(...)` becomes `it.skip(...)`
- `toBe(42)` becomes `toBeDefined()`
- the body gets wrapped in a try/catch that swallows
- the expected value is changed to whatever the broken code currently returns

That last one is the dangerous one. The diff is two characters. The test still exists, still runs, still passes, and now encodes the bug as the specification. Six months later somebody fixes the bug properly, the test goes red, and they put the bug back to make it green.

### The fix is one line

Restore the tests from git before you judge anything.

```bash
# The agent may edit tests while it works. The judge never sees those edits.
git checkout -- '**/*.test.ts' '**/*.spec.ts' 2>/dev/null || true

if output=$(pnpm test 2>&1); then
  echo "green on attempt $attempt"
  exit 0
fi
```

Two lines, and they close the whole category. The agent is still free to open test files, read them, use them to work out what is expected — it just cannot change the exam before sitting it.

If you want the loop to tell you *why* an attempt looked green when it was not, make a note of what it touched before you throw the edits away:

```bash
cheated=$(git diff --name-only -- '**/*.test.ts' '**/*.spec.ts')
if [[ -n "$cheated" ]]; then
  echo "attempt $attempt edited the spec: $cheated" >&2
fi
```

That line is worth more as a signal than as a guard. An agent that keeps reaching for the test file is usually telling you the task is underspecified, not that it is lazy.

One caveat worth saying out loud: if the job *is* to write tests, this guard is wrong and you need a different critic — coverage, a mutation score, something that cannot be satisfied by an empty `it()`. Do not bolt it on without deciding which job you are running.

## 2. The rut

A loop running is not a loop moving.

The failure looks like this. Attempt three makes a change, the suite fails. Attempt four sees the same failure, makes the same change, fails identically. So does five. So does six. The budget runs out, the script exits one, and you have paid for four attempts that were all the same attempt.

This is not the model being stupid. It is the model being consistent, which is normally the thing you want from it. Same context in, same completion out. Part one told you to hand back only the last failure — good for the token bill, and it also means a stuck loop has nothing new to go on, ever.

A loop should be able to notice this about itself. The trick is to fingerprint the failure rather than compare it:

```bash
# Strip digits before hashing. Line numbers, durations and timestamps
# change on every run; the bug does not.
fingerprint() {
  tr -d '0-9' <<< "$1" | shasum | cut -c1-8
}
```

Then count the repeats and stop when there is nothing left to learn:

```bash
fp=$(fingerprint "$failure")

if [[ "$fp" == "$prev_fp" ]]; then
  (( stuck++ ))
else
  stuck=0
fi
prev_fp=$fp

if (( stuck >= 2 )); then
  echo "same failure three times running — a rut, not persistence" >&2
  exit 2
fi
```

Note the separate exit code. Out of attempts might just mean the task was big. Stuck means the next attempt is pointless, and if anything upstream is deciding whether to escalate, it deserves to know which one happened.

What you do about a rut is a judgement call. Escalating to a stronger model works sometimes. Widening the context you were so careful to trim works sometimes. Stopping and asking a person always works. What never works is running the same attempt a fourth time.

## 3. The budget that was not a budget

`MAX_ATTEMPTS=6` looks like a budget. It counts the wrong thing.

Attempts are not interchangeable. One might be a thirty-second edit. The next might be forty minutes of the agent wandering a monorepo, reading two hundred files and burning several hundred thousand tokens before it produces a diff. Six of those is not six times the first one. You capped the one quantity you do not care about and left the two you do — money and wall-clock — unbounded.

Bound the thing you would actually regret:

```bash
DEADLINE=$(( $(date +%s) + 20 * 60 ))   # the whole run, not one attempt
ATTEMPT_TIMEOUT=300                      # and no single attempt gets to hang

while (( attempt <= MAX_ATTEMPTS )); do
  if (( $(date +%s) >= DEADLINE )); then
    echo "out of time after $((attempt - 1)) attempts" >&2
    exit 3
  fi

  timeout "$ATTEMPT_TIMEOUT" agent --prompt "$prompt" || true
  ...
done
```

`MAX_ATTEMPTS` stays, because it is still a useful sanity bound. It is just no longer the only one, and no longer the one that matters.

## 4. The write that landed twice

Part one said every tool a loop can reach has to be safe to call twice, gave it one paragraph and a four-line sample, and moved on.

That paragraph was doing far too much work.

The scenario is ordinary. The agent calls a tool that creates something. The call takes longer than the client's timeout. The client gives up, the loop retries. The original request was never cancelled — only abandoned — so it completes anyway, and now there are two.

What makes this worse than the other three is that nothing goes red. The critic passes. The loop exits zero. You find out from a user, or from a reconciliation report, or you do not find out.

The real fix is more than a `findOne` before an `insert`, because that check is itself a race, and because making the retry return *the same answer* as the original turns out to be the hard part rather than the easy one. That is a post of its own, and it is [the next one](/blog/idempotency-keys).

## Putting it back together

All of it, in one file:

```bash
#!/usr/bin/env bash
# fix-tests.sh — part two. Four ways to stop, three of them on purpose.
set -uo pipefail

MAX_ATTEMPTS=6
ATTEMPT_TIMEOUT=300
DEADLINE=$(( $(date +%s) + 20 * 60 ))

attempt=1
stuck=0
prev_fp=""
prompt="The test suite is failing. Fix the cause, not the test."

fingerprint() { tr -d '0-9' <<< "$1" | shasum | cut -c1-8; }

while (( attempt <= MAX_ATTEMPTS )); do
  if (( $(date +%s) >= DEADLINE )); then
    echo "out of time after $((attempt - 1)) attempts" >&2
    exit 3
  fi

  echo "── attempt $attempt/$MAX_ATTEMPTS"
  timeout "$ATTEMPT_TIMEOUT" agent --prompt "$prompt" || true

  # Did it reach for the exam paper?
  cheated=$(git diff --name-only -- '**/*.test.ts' '**/*.spec.ts')
  [[ -n "$cheated" ]] && echo "   note: attempt touched $cheated" >&2

  # Judge against the tests as committed, never as edited.
  git checkout -- '**/*.test.ts' '**/*.spec.ts' 2>/dev/null || true

  if output=$(pnpm test 2>&1); then
    echo "green on attempt $attempt"
    exit 0
  fi

  failure=$(tail -n 60 <<< "$output")
  fp=$(fingerprint "$failure")

  if [[ "$fp" == "$prev_fp" ]]; then (( stuck++ )); else stuck=0; fi
  prev_fp=$fp

  if (( stuck >= 2 )); then
    echo "same failure three times running — a rut, not persistence" >&2
    exit 2
  fi

  prompt="The test suite is still failing. Fix the cause, not the test.

$failure"
  (( attempt++ ))
done

echo "out of attempts — last failure above" >&2
exit 1
```

Fifty lines against the original twenty, and nearly all of the new ones are about stopping. That ratio is not an accident. Starting work is the trivial part of a control system.

## If you only take one thing

Take the `git checkout` line.

The other three cost you money and time, and you will notice them. The bill is bigger than you expected, or the loop sits there for an hour, or the same error scrolls past four times and you recognise it. Annoying, visible, fixable.

The first one costs you a green checkmark you believed. You will not notice it, because the entire reason you built the loop was to stop reading every turn — and a loop you cannot trust is worse than no loop at all, since now you are not reading the turns *and* you are not getting the verification you traded them for.

Make the exam unreachable. The rest is tuning.
