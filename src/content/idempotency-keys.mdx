## What idempotent actually means

Doing it twice leaves the world in the same state as doing it once.

Some of HTTP is already there by construction. `GET` changes nothing. `PUT /users/7` with a full body sets the same fields to the same values no matter how many times it arrives. `DELETE /orders/4` removes the order and then has nothing left to remove.

`POST /payments` is the opposite. Its whole job is to create something new each time it is called. That is not a flaw to be designed away — it is what the endpoint is for. So you cannot make it naturally idempotent. You have to give the caller a way to say *this is the same request I sent you a moment ago*, and that is all an idempotency key is: a string, chosen by the client, that names one logical operation.

```http
POST /v1/payments HTTP/1.1
Idempotency-Key: 9f2a1c84-6d3e-4b70-9f21-0ac41b8e5d12
Content-Type: application/json

{ "order_id": 50912, "amount": 240000, "currency": "INR" }
```

Same key arriving twice means: you already have this one, give me back what you gave me the first time.

## The obvious fix has a hole in it

Almost everyone writes this first:

```ts
// Don't ship this.
async function createPayment(input: PaymentInput, key: string) {
  const existing = await db.payments.findOne({ idempotencyKey: key });
  if (existing) return existing;

  return db.payments.insert({ ...input, idempotencyKey: key });
}
```

It reads fine. It is wrong, and it is wrong in exactly the situation it was written for.

Two retries of the same request can be in flight at the same time — that is the normal case, not the exotic one, because the client retried precisely because the first one was slow. Both run the `findOne`. Both find nothing, because neither has inserted yet. Both insert.

The check and the write are two separate round trips, and anything can happen in the gap between them.

## Let the database decide

Stop asking whether the key exists. Try to claim it, and let a unique index settle the argument. Exactly one writer can win, the loser finds out by getting an error, and there is no window because the index check and the write are the same operation.

```sql
CREATE TABLE idempotency_keys (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id       BIGINT       NOT NULL,
  endpoint      VARCHAR(120) NOT NULL,
  idem_key      VARCHAR(255) NOT NULL,
  request_hash  CHAR(64)     NOT NULL,
  state         ENUM('in_flight','completed') NOT NULL DEFAULT 'in_flight',
  status_code   SMALLINT     NULL,
  response_body JSON         NULL,
  created_at    TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  expires_at    TIMESTAMP    NOT NULL,

  UNIQUE KEY uq_claim (user_id, endpoint, idem_key)
);
```

Three columns in that unique key, and each one is load bearing.

`user_id` scopes the key to the person who sent it. Without it, two customers who both send `retry-1` collide, and the second one is handed the first one's payment receipt. Keys are chosen by clients, so you must assume they are guessable, repeated, and occasionally just the string `test`.

`endpoint` stops a key reused across two different operations from matching. The same mobile app sending `abc` to `/payments` and to `/refunds` means two different things.

`idem_key` is the client's string.

## Store the answer, not the fact

Here is the part that gets skipped, and it is the part that decides whether any of this actually helps the customer.

Knowing the request already happened is not enough. The retry is still sitting there waiting for a response, and it needs *the same response* — the same body, the same status code, the same payment id. If the duplicate gets a bare `409 Conflict`, you have prevented the double charge and still broken the client, which is now looking at an error for a payment that succeeded.

So `response_body` and `status_code` are columns. On a replay you return what you stored, byte for byte, and tell the caller that is what you did:

```
HTTP/1.1 201 Created
Idempotent-Replay: true
```

That header is not decoration. It is how someone reading a support ticket at two in the morning works out whether they are looking at one payment or two.

## Three things a duplicate can mean

Once the claim fails, you load the existing row, and there are exactly three cases.

**Same key, same body, already finished.** Replay the stored response. This is the happy path and the whole point of the exercise.

**Same key, different body.** Refuse it. Someone has reused a key for a different operation — almost always a client bug, occasionally something worse — and the one thing you must not do is guess which of the two requests they meant. Compare a hash of the body and return `422`:

```ts
const requestHash = sha256(canonicalJson(req.body));
```

Note `canonicalJson`, not `JSON.stringify`. Two clients can send the same fields in a different order and `JSON.stringify` will hash them differently, so you would reject a legitimate retry. Sort the keys before hashing, recursively, and decide what you do about floats before you find out the hard way.

**Same key, same body, still running.** The first request has not finished yet. Do not run the work again, and do not block holding a connection open either:

```
HTTP/1.1 409 Conflict
Retry-After: 2
```

### The stuck key

That `in_flight` state has a trap in it. If the process handling the first request dies — deploy, OOM, pod evicted — the row sits there forever, and every retry of that payment gets `409` until the end of time. You have replaced a double charge with a payment that can never be made.

Treat the claim as a lease rather than a lock. If a row has been `in_flight` for longer than any sane request could run, let the next caller take it over:

```sql
UPDATE idempotency_keys
   SET created_at = NOW()
 WHERE user_id = ? AND endpoint = ? AND idem_key = ?
   AND state = 'in_flight'
   AND created_at < NOW() - INTERVAL 2 MINUTE;
```

If that updates one row, you own the claim and can proceed. If it updates zero, somebody else is legitimately still working and `409` is the right answer.

Pick the lease window from your actual p99, not from a round number you like.

## The client bug that undoes everything

All of the above is wasted if the key is generated in the wrong place. This is the single most common way idempotency gets implemented and still does not work:

```ts
// Wrong. A fresh key on every attempt means every attempt is a new operation,
// and the server has no way to know they were ever related.
await retry(() =>
  fetch("/v1/payments", {
    method: "POST",
    headers: { "Idempotency-Key": crypto.randomUUID() },
    body,
  }),
);
```

The key belongs to the operation, not to the attempt. Generate it once, before the first try, and reuse it for every retry of that same intent:

```ts
const idempotencyKey = crypto.randomUUID();

await retry(() =>
  fetch("/v1/payments", {
    method: "POST",
    headers: { "Idempotency-Key": idempotencyKey },
    body,
  }),
);
```

Two lines apart in the source, and the difference between a system that deduplicates and one that has an expensive header.

If the user can trigger the operation again by tapping the button a second time, that is a different question and a different fix — the key should then be derived from something stable about the intent, like the cart or the order id, so a double tap is also caught.

## Wiring it into NestJS

This is interceptor-shaped work — it wraps the handler, it needs the request before and the response after, and it has nothing to do with payments specifically.

```ts
@Injectable()
export class IdempotencyInterceptor implements NestInterceptor {
  constructor(private readonly store: IdempotencyStore) {}

  async intercept(ctx: ExecutionContext, next: CallHandler) {
    const http = ctx.switchToHttp();
    const req = http.getRequest();
    const key = req.header("Idempotency-Key");

    if (!key) {
      throw new BadRequestException("Idempotency-Key header is required");
    }

    const scope = {
      userId: req.user.id,
      endpoint: `${req.method} ${req.route.path}`,
      key,
      requestHash: sha256(canonicalJson(req.body)),
    };

    const claim = await this.store.claim(scope);

    if (claim.kind === "replay") {
      http.getResponse().status(claim.statusCode).set("Idempotent-Replay", "true");
      return of(claim.body);
    }
    if (claim.kind === "in_flight") {
      http.getResponse().set("Retry-After", "2");
      throw new ConflictException("This request is still being processed");
    }
    if (claim.kind === "mismatch") {
      throw new UnprocessableEntityException(
        "This Idempotency-Key was already used with a different body",
      );
    }

    return next.handle().pipe(
      concatMap(async (body) => {
        await this.store.complete(scope, 201, body);
        return body;
      }),
      catchError((err) =>
        from(this.store.settleFailure(scope, err)).pipe(
          mergeMap(() => throwError(() => err)),
        ),
      ),
    );
  }
}
```

`settleFailure` is where the thinking is. A `4xx` is deterministic — the same request will fail the same way — so record it as completed and let retries replay the error. A `5xx` or an unknown crash is not deterministic, so release the claim and let the client genuinely try again. Collapsing those two into one branch is how you end up permanently refusing a payment because the database had a bad five seconds.

  Write the key row and do the work in the same database transaction. If they
  are separate, there is a moment where one has happened and the other has
  not — and whichever way round you arrange it, that moment is a bug.
</Callout>

## Two things the transaction cannot save you from

**The next hop.** Your transaction covers your database. It does not cover the HTTP call to the payment gateway sitting in the middle of it. If that call times out, you are in exactly the position your client was in at the top of this post, one layer down. The answer is the same answer: pass an idempotency key onward too. Every serious payment provider accepts one. Your guarantee is only as strong as the weakest hop in the chain.

**Expiry.** Keys cannot live forever; the table would grow without bound. Twenty-four hours is the common choice and a reasonable one. But be clear about what expiry means — once the row is gone, a retry carrying that key is just a new request, and it will charge again. That is not a reason to skip expiry. It is a reason to document the window and make sure your client's retry budget is comfortably inside it.

## Where this started

Last week's post was about agent loops, and the fourth failure in it was a tool call that ran twice because the loop retried something it should not have. I said then that it deserved its own post. This is it, and the reason it deserved one is that the fix is not a line of code — it is a schema, a state machine, a header contract and a decision about what a failure means.

Which is also why this is old ground rather than new. Payment systems have been retrying over unreliable networks for decades and the solution has been settled for most of that time. The only thing that changed is who is doing the retrying.

It used to be a phone on a bad connection. Now it is also a loop you wrote, running unattended at three in the morning, and it is considerably more persistent than the phone ever was.
